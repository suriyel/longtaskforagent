# Long-Task Agent Architecture

## Core Concept

Long-running tasks exceed a single context window. The solution: split work into a **Requirements Phase** (SRS), a **Design Phase**, an **Initializer Session** (runs once), and multiple **Worker Sessions** (run iteratively), connected by persistent artifacts on disk.

## Persistent Artifacts

### 1. `task-progress.md`

Session log that bridges context gaps. Each worker session appends an entry.

```markdown
# Task Progress Log

## Project: [name]
Created: [date]

---

### Session 1 — [date/time]
**Focus**: User authentication API endpoints
**Completed**:
- POST /auth/login with JWT
- POST /auth/register with validation
- Unit tests for auth module (12/12 passing)
**Issues**: None
**Next Priority**: Password reset flow (feature #5)
**Git Commits**: a1b2c3d, e4f5g6h
```

### 2. `feature-list.json`

Structured task inventory. JSON format prevents accidental model corruption. Also carries SRS-derived project-wide context (`constraints`, `assumptions`) so Workers read it in every Orient phase.

```json
{
  "project": "project-name",
  "created": "2025-01-15",
  "constraints": [
    "Must run offline — no external API calls permitted",
    "Python 3.8+ only — no 3.10+ match syntax"
  ],
  "assumptions": [
    "JWT validation handled by API Gateway; business layer must NOT re-validate",
    "Input data is pre-sanitised before reaching this service"
  ],
  "features": [
    {
      "id": 1,
      "category": "core",
      "title": "User login with JWT",
      "description": "POST /auth/login returns JWT token on valid credentials",
      "priority": "high",
      "status": "passing",
      "srs_trace": ["FR-001"],
      "verification_steps": [
        "Send POST with valid credentials, verify 200 + token",
        "Send POST with invalid credentials, verify 401",
        "Verify token contains correct claims"
      ],
      "dependencies": []
    },
    {
      "id": 2,
      "category": "core",
      "title": "User registration",
      "description": "POST /auth/register creates new user account",
      "priority": "high",
      "status": "failing",
      "srs_trace": ["FR-002"],
      "verification_steps": [
        "Send POST with valid data, verify 201",
        "Send POST with duplicate email, verify 409",
        "Verify password is hashed in DB"
      ],
      "dependencies": []
    }
  ]
}
```

**Rules**:
- Status is only `"failing"` or `"passing"` — never `"partial"` or `"in-progress"`
- `srs_trace` is required per feature — maps to SRS requirement IDs for traceability
- `verification_steps` is optional — if present, provides supplementary test context
- Features marked `"passing"` must be re-verified at session start

### 3. `RELEASE_NOTES.md`

Living document that tracks all user-visible changes. Updated after **every feature completion** to ensure release notes stay in sync with code.

```markdown
# Release Notes

## [Unreleased]

### Added
- User login with JWT authentication (#1)
- User registration with email validation (#2)

### Changed
- (none yet)

### Fixed
- (none yet)

---

## [0.1.0] — 2025-01-15
### Added
- Initial project scaffold
```

**Rules**:
- Use [Keep a Changelog](https://keepachangelog.com/) format: Added, Changed, Deprecated, Removed, Fixed, Security
- Reference feature IDs from `feature-list.json` in each entry
- Move entries from `[Unreleased]` to a versioned section when milestones are reached
- Update after every feature completion — never defer to end of session

### 4. `examples/` Directory

Optional directory for scenario-based usage examples. Created during Init; examples can be added manually as the project matures.

**Rules**:
- Scenario-oriented, not feature-oriented — one example may span multiple features
- Examples MUST be runnable or follow-along — not just code snippets
- Name pattern: `<NN>-<scenario-name>.<ext>` (e.g., `01-quick-start.py`)
- `examples/README.md` index lists all examples with prerequisites and run commands
- Skip non-externalizable features (infrastructure, internal logic, config scaffolding)

### 5. Git History

- Each session commits with descriptive messages
- Enables reverting broken changes
- Provides context for subsequent sessions via `git log`

### 6. `long-task-guide.md`

Worker session guide **generated by the LLM** during the Initializer phase, tailored to the project's tech stack and characteristics. Contains the full workflow for each context cycle. Lives in the project root. Validated by `validate_guide.py` for structural completeness.

## Requirements Phase (Phase 0a)

Runs **before** the Design phase. Produces a structured SRS aligned with ISO/IEC/IEEE 29148.

**Hard gate**: No design, feature decomposition, scaffolding, or coding until SRS is approved.

1. **Explore context** — read requirement doc, existing code; detect SRS template
2. **Structured elicitation** — ask clarifying questions one at a time, challenge each requirement against 8 quality attributes (correct, unambiguous, complete, consistent, ranked, verifiable, modifiable, traceable)
3. **Classify requirements** — functional (FR-xxx) / constraint (CON-xxx) / assumption (ASM-xxx) / interface (IFR-xxx) / exclusion (EXC-xxx)
4. **Write requirements** — apply EARS templates, assign unique IDs, write Given/When/Then acceptance criteria
5. **Validate SRS** — anti-pattern detection (weasel words, compound requirements, design leakage), completeness cross-check
6. **Section-by-section approval** — present SRS to user, get approval per section
7. **Save SRS document** — `docs/plans/YYYY-MM-DD-<topic>-srs.md`

## Design Phase (Phase 0b)

Runs **after** SRS is approved, **before** the Initializer. Takes SRS as input, focuses on HOW.

**Hard gate**: No feature decomposition, scaffolding, or coding until design is approved.

1. **Read SRS** — extract design drivers (constraints, interface requirements)
2. **Explore technical context** — existing code, frameworks, runtime environment
3. **Propose 2-3 approaches** — with explicit trade-offs, evaluate against SRS constraints
4. **Get section-by-section approval** — architecture, data model, API, UI, testing
5. **Save design document** — `docs/plans/YYYY-MM-DD-<topic>-design.md` (uses custom template if provided)

## Initializer Session Workflow

The initializer runs **once** after both SRS and design are approved. It reads from **two** approved documents:
- **SRS** (`docs/plans/*-srs.md`) — for functional requirements, constraints, assumptions, glossary, user personas
- **Design** (`docs/plans/*-design.md`) — for tech stack, architecture, testing strategy

Its job:

1. **Read approved SRS + design documents** — from `docs/plans/`
2. **Run `init_project.py`** — scaffolds deterministic artifacts: `feature-list.json`, `task-progress.md`, `RELEASE_NOTES.md`, `examples/`, `scripts/`, `docs/plans/`
3. **LLM generates `long-task-guide.md`** — project-tailored Worker guide based on SKILL.md + references + design doc; only includes the project's language-specific commands; validated by `validate_guide.py`
4. **Populate `feature-list.json`** — from SRS: `constraints[]` (CON-xxx), `assumptions[]` (ASM-xxx), FR-xxx → functional features with `srs_trace` (requirement IDs) and optional `verification_steps`
5. **Scaffold project skeleton** — directory structure, config files, package.json / pyproject.toml etc. (based on design doc architecture)

### Artifact Generation: Script vs LLM

| Artifact | Generated by | Source Document | Rationale |
|----------|-------------|-----------------|-----------|
| `feature-list.json` (schema) | Script | — | Deterministic structure needed for validation tools |
| `task-progress.md` | Script | — | Universal format template |
| `RELEASE_NOTES.md` | Script | — | Universal Keep a Changelog template |
| `examples/README.md` | Script | — | Universal format template |
| `long-task-guide.md` | **LLM** | Design | Project-tailored; only relevant language/tools; validated by `validate_guide.py` |
| `features[]` content | **LLM** | **SRS** | FR-xxx → features with `srs_trace` (requirement IDs) and optional `verification_steps` |
| `constraints[]` content | **LLM** | **SRS** | Extracted from SRS "Constraints" section (CON-xxx) |
| `assumptions[]` content | **LLM** | **SRS** | Extracted from SRS "Assumptions" section (ASM-xxx) |

## Worker Session Workflow

> Authoritative workflow definition: `skills/long-task-work/SKILL.md`. Cycle: Orient → Feature Design → TDD Red → TDD Green → TDD Refactor → Quality Gate Loop (check → coverage fix → mutation fix → recheck, max 20 rounds) → Persist → End Session. One feature per cycle; external `scripts/auto_loop.py` handles multi-feature automation.

## Anti-Patterns to Avoid

| Anti-Pattern | Why It Fails | Correct Approach |
|---|---|---|
| Attempting multiple features in parallel | Context exhaustion, cascading failures | One feature per cycle |
| Using markdown for feature list | Models tend to corrupt/reformat markdown | Use JSON for structured data |
| Skipping requirements phase | Incomplete requirements cause rework | Run requirements elicitation, produce approved SRS first |
| Skipping design phase | Ad-hoc design causes inconsistency | Run design phase after SRS, get approval first |
| Skipping progress file update | Next session wastes tokens rediscovering state | Always update before ending session |
| Guess-and-fix debugging | Random fixes waste time, may introduce new bugs | Follow systematic debugging — trace root cause |
