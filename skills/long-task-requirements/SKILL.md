**语言规则**：用中文（简体）回复用户。所有生成的文档、报告和面向用户的输出用中文。Skill 名称、代码标识符、JSON 字段名保持英文。

# 需求打磨与 SRS 生成

输入：用户提供的需求文档（可能已近乎详细设计）+ 现有代码库上下文（若存量）。
动作：直接从用户输入提取候选 FR，交叉对照存量 ESI，用 EARS 改写并定量，单轮批准。
不做多轮挖掘式澄清，不做复杂度打分路由。

<HARD-GATE>
在呈现 SRS 并获得用户批准之前，不可调用任何设计 skill、实现 skill、编写任何代码、搭建任何项目、或采取任何设计/实现行动。每个项目都适用，无论看起来多简单。
</HARD-GATE>

## Step 1 — 读上下文

1. 完整阅读用户提供的需求文档/想法描述。逐段标注：哪些是目标声明、哪些是行为规约、哪些是约束、哪些是实现偏好。
2. 检查 `docs/rules/`（若存在且已填充）— Phase 0-pre 扫描器提取的代码库约定：
   - `coding-constraints.md` — 2/3方件库约束、禁止的 API、内部库强制要求
   - `build-and-compilation.md` — 构建系统约束
   - `coding-style.md` — 风格约束
3. 加载 SRS 模板：用户指定路径优先，否则 `docs/templates/srs-template.md`。验证 `.md` 且含至少一个 `## ` 标题。

## Step 1.4 — Brownfield 检测（内部，不与用户交互）

判定为存量系统的信号（满足任意 2 个即 `is_brownfield = true`）：
1. `docs/rules/` 存在且含 ≥1 个非桩 `.md`
2. `docs/explore/codebase-research.md` 存在
3. 用户描述含存量语言（"现有"、"已有"、"扩展"、"修改"、具体模块/文件路径）
4. Git 历史 ≥5 commits 且源文件 >3 个

内部记录 `is_brownfield` 与置信度，不询问用户。

## Step 1.6 — 针对性存量探索（仅 brownfield）

**触发**：`is_brownfield = true` 且用户描述包含具体功能 / 领域区域 / 模块关键词。
**跳过**：新建项目；或用户描述过于模糊无法推导 focus。

执行：
1. 从用户描述提取领域关键词（如"认证"/"支付"/"数据管道"），推导 `--focus` 维度。
2. 推断 `--path`（若用户提及具体目录）。
3. 深度默认省略（让 explore 按 LOC 自检）；用户输入明显窄范围可降。
4. DISPATCH：

   > **DISPATCH** 创建独立 SubAgent（使用 General 或 Agent）— 在 subagent 中加载并执行 skill `long-task:long-task-explore`
   > Depth: {省略或推导}
   > Focus: {推导的维度}
   > Path: {推导的路径或 "."}
   > User question: "{用户描述摘要}"

5. 若返回有用结果 → 按 `references/brownfield-adaptation.md` §A 构建 ESI 表（内部态）。
6. BLOCKED / 无有用结果 → 静默跳过，仍照常进入 Step 2。此步非阻塞。

## Step 2 — 打磨用户输入（内部，不与用户交互）

从用户输入文档直接提取候选 FR。**不问用户需求是什么 — 用户已经写了。**

1. **提取**：逐段读用户输入。每段描述可观察系统行为的片段 → 1 个候选 FR。保留用户原词，标注来源段落。
2. **分类**：每个候选归入 功能 / 约束 / 假设 / 接口 / 排除（见 Step 4 的 ID 前缀）。实现细节（"用 Redis 做缓存"）归为 假设 或 约束 或 接口，**不**作为 FR。
3. **交叉对照 ESI**（仅 brownfield）：
   - 每个候选 FR 与 ESI "已确立"维度对比
   - 标注：`NEW` / `MODIFY` / `EXTEND` / `REUSE`（REUSE 转为 ASM-xxx，不成为 FR — 见 `references/brownfield-adaptation.md` §C）
4. **识别 gap**：列出必须向用户确认的空白：
   - **冲突**：用户输入内部矛盾，或用户输入 ↔ ESI 冲突
   - **缺 AC**：用户只描述成功路径，未提错误/边界
   - **未声明约束**：用户输入暗示但未明说的硬性限制
   - **范围边界模糊**：用户描述边界与 `docs/rules/` 或 ESI 发生拉扯的区域

产出（内部态）：候选 FR 草表 + gap 清单。

## Step 3 — Gap Fill（单轮 AskUserQuestion，≤4 问）

**仅**针对 Step 2 标注的 gap 提问。不重复用户已在输入文档中写明的内容。

若 brownfield：使用 `references/brownfield-adaptation.md` §B 的校核式问句模板（"我从输入提取到 FR-X。它与 ESI 现存 Y 是替换/扩展/并行？"）。

**Gap Fill 输出**：用户回答整合到候选 FR 草表与 §1.2 排除范围 / §6 约束 / §7 假设。

**升级逃生门**：若 Step 2 产出的候选 FR ≤ 3 且无明确目标（用户输入过于模糊）→ 告知用户"输入不足以打磨，切换到挖掘模式"→ 进入 3-5 轮扁平提问（每轮 ≤4 问，覆盖问题陈述、角色、范围边界、能力清单、错误路径）。挖掘完成后回到 Step 4。

## Step 4 — EARS 编写 + 图表

### 4.1 分类与 ID

| 类别 | ID 前缀 | 描述 |
|------|---------|------|
| 功能 | FR-001 | 可观察的系统行为 |
| 约束 | CON-001 | 限制解决方案空间的硬性限制 |
| 假设 | ASM-001 | 假定为真的信念；记录失效风险 |
| 接口 | IFR-001 | 外部系统契约 |
| 排除 | EXC-001 | 明确不在范围内 |

### 4.2 EARS 模板

| 模式 | 模板 | 适用场景 |
|------|------|---------|
| 普遍型 | The system shall `<action>`. | 始终生效 |
| 事件驱动型 | When `<trigger>`, the system shall `<action>`. | 响应事件 |
| 状态驱动型 | While `<state>`, the system shall `<action>`. | 模式/状态相关 |
| 异常行为型 | If `<condition>`, then the system shall `<action>`. | 错误处理 |
| 可选型 | Where `<feature/config>`, the system shall `<action>`. | 可配置能力 |

每个 FR 配：至少一个 Given/When/Then 验收标准；MoSCoW 优先级；来源（用户输入段落 / ESI gap / 走查发现）。

### 4.3 图表

- **用例视图**（§3.1）：`graph LR`，角色为 `Actor((Name))`，FR-xxx 作为 `subgraph System Boundary` 内的节点，角色→用例绘制边。
- **流程图**（§4.1）：每个有 3+ 个顺序步骤或分支的功能区域一个 `flowchart TD`。起止 `([label])`，决策 `{condition?}`，标注 `-- YES -->` / `-- NO -->`。

### 4.4 语言精炼

- 一句能说清的不用两句；一个词能表达的不用短语
- EARS 声明直达行为，不加修饰语与背景解释
- Given/When/Then 每段 ≤1 行
- 排除"为了...所以..."式动机（动机归 §1.3）
- 术语表仅收录有歧义的术语
- 存量：不重复 ESI 已确立能力，仅写增量

## Step 5 — 粒度分析（双向定量）

目标：每 FR 约产生 1,000 行实现代码（不含 UT），对应一个 Worker 会话 ~50% 上下文。

### 5.0 配置

| 上下文窗口 | 每 FR 目标 AC 数 | 实现范围 |
|------------|----------------|----------|
| ≤ 200K tokens | 3-12 | ~1,000 行 |
| > 200K tokens | 5-20 | ~1,000 行 |

### 5.1 过大检测（G1-G6）— 拆分

| # | 启发式 | 信号 |
|---|--------|------|
| G1 | 多角色 | 2+ 角色执行不同操作 |
| G2 | CRUD 捆绑 | 增删改查为单一需求 |
| G3 | 场景爆炸 | 4+ AC 覆盖不同行为路径 |
| G4 | 跨层关注 | 后端 + UI 在同 FR |
| G5 | 多状态行为 | 3+ 不同状态/模式 |
| G6 | 时序耦合 | 触发事件 + 延迟/定时后果 |

候选 → 识别原子行为，单一职责测试，保持可追溯（FR-003 → FR-003a/b），重新验证子项。

### 5.2 过小检测（S1-S4）— 合并

| # | 启发式 | 信号 | 操作 |
|---|--------|------|------|
| S1 | 微小新增 | 单字段/常量/配置，≤1 AC | 合并到父实体 FR |
| S2 | 单 AC 无负例 | 仅 1 AC 且无错误/边界 | 充实 AC，或合并到共享实体/端点的相关 FR |
| S3 | 纯数据回显 | 无转换地显示另 FR 产物 | 作为垂直切片合并 |
| S4 | 仅配置/脚手架 | 环境/依赖安装，无业务逻辑 | 合并为 Foundation FR |

**合并规则**：
- 内容保留强制 — 被吸收 FR 的 EARS + 全部 AC + 描述文本完整并入主 FR，不摘要化
- 合并后若 AC > 20 → G3 重新触发 → 按更好接缝拆分
- 合并 FR 必须共享主角色 + 功能区域
- 同 FR 同时触发 G 和 S → G 优先（先拆，再对子项重查 S）
- 合并后按顺序重编 FR ID 并更新全部交叉引用（用例视图、流程图、可追溯矩阵）

### 5.3 决策阈值

| 候选数量 | 操作 |
|---------|------|
| 0 | 跳过 |
| 1-3 | 自动应用，内联呈现理由 |
| 4+ | AskUserQuestion 批准 |

### 5.4 FR 粒度确认（强制）

所有拆分/合并/重编号后，呈现最终 FR 表供用户确认：

| FR ID | 标题 | AC 数 | 预估 LOC | 变更？ | 备注 |
|-------|------|-------|---------|--------|------|
| | | | | 从 FR-X 拆分 / 吸收 FR-Y / 未变更 | |

问："每 FR 目标 ~1,000 行实现代码（不含 UT）。合并 FR 保留被吸收内容完整并集。确认粒度或指出需进一步拆分/合并。"
- 确认 → Step 5.5
- 请求调整 → 应用、重编号、重新呈现

即使 0 候选（无拆分/合并）也呈现 FR 列表供确认。

### 5.5 单轮模式确认（强制）

通过 AskUserQuestion：

> "最终 FR 列表 {N} 个。**单轮模式可用**：全部 FR 在本轮（wave 0）实现，不延迟。每个 FR 映射到一个功能；Worker 每会话一个功能。若任何 FR 估计 > ~1,000 行实现代码，考虑进一步拆分。
> [启用单轮模式] / [跳过 — 进入延迟分析]"

- 启用 → SRS 元数据记 `Single-Round: Yes`。Step 6 仍跑但只呈现确认摘要。
- 跳过 → Step 6 正常延迟分析。

## Step 6 — 范围适配与延迟

评估所有需求是否属于本轮。标准：优先级、依赖、完整性、风险、范围预算。

规则：
- Must 级 FR 不自动延迟
- 若 FR-X 依赖 FR-Y，两者同进同出
- 延迟积压保留 EARS + AC 供 increment 拾取

若有延迟 → 生成 `docs/plans/YYYY-MM-DD-<topic>-deferred.md`。

## Step 7 — SRS 质量审查门

DISPATCH：

> **DISPATCH** 创建独立 SubAgent（使用 General 或 Agent）— SRS 合规审查员
> Prompt：读取 `skills/long-task-requirements/prompts/srs-reviewer-prompt.md` 中的审查员指令
> Input：项目上下文、完整 SRS 草稿、需求 ID 列表
> 严格按 prompt 执行审查，返回 PASS/FAIL 判决表

全部检查 PASS 方可继续：R / A / C / S / B（brownfield 时） / D / G / Z。

FAIL 双轨：
- **USER-INPUT 项** → AskUserQuestion 附定向问卷，不倒完整审查报告
- **LLM-FIXABLE 项** → 并行自动修复

最多 2 次重新分派。第 2 轮仍失败 → 上报用户。

## Step 8 — 呈现、保存、过渡

### 8.1 呈现批准

默认合并单次批准（打磨模式 — 用户输入已具结构）。
> 20 FR 或用户明确要求分章节 → 按 §1-§2 / §3 / §4 / §5-§7 四段呈现，整合后进下一段。

### 8.2 保存

读取 Step 1 加载的模板：
1. 保留标题结构
2. 每个标题下替换指导文本为批准内容
3. 顶部元数据若无则加：`Date`、`Status`、`Standard`、`Template` 路径、`Single-Round: Yes/No`
4. 模板未覆盖的章节：标记"[不适用]"
5. 批准内容若无匹配章节：追加为"附加说明"

保存到 `docs/plans/YYYY-MM-DD-<topic>-srs.md`，延迟积压一并保存。Git commit。

### 8.3 过渡

调用 `long-task:long-task-design`。

**终态：调用 long-task-design。**

## 反模式

| 合理化 | 正确回应 |
|--------|---------|
| "这太简单了，不需要 SRS" | 打磨模式本身就是简单路径。短 SRS 可接受。 |
| "用户输入是原文，直接转设计" | 用户输入混合了目标/行为/实现偏好。SRS 增加分类、完整性、可测试性。 |
| "让我先问用户想要什么" | 用户已写在输入文档。先读、先提取、再只问 gap。 |
| "ESI 已覆盖的能力仍写成 FR" | REUSE 转 ASM-xxx 或根本不记。FR 只写增量。 |
| "这个 FR 小但清晰，不合并" | S1-S4 启发式 — 过小 FR 浪费会话固定开销。 |
| "所有需求都属于本轮" | Step 6 评估；延迟低优先级保留 EARS + AC 到积压。 |
| "用户输入暗示了设计方案就跳 SRS" | 需求定义 WHAT，设计 = HOW。两份都要。 |
| "无障碍不适用于此项目" | 任何用户界面都有 WCAG 2.1 AA 基线。 |
| "隐私在设计处理" | 隐私需求必须在 SRS — 数据模型与同意流程依赖它们。 |
