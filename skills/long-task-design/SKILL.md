**语言规则**：你必须用中文（简体）回复用户。所有生成的文档、报告和面向用户的输出必须用中文编写。Skill 名称、代码标识符和 JSON 字段名保持英文。

# 设计文档生成

以已批准的 SRS 为输入。提出实现方案，逐章节获取设计批准，产出回答 HOW 的设计文档 — SRS 回答 WHAT。

<HARD-GATE>
在呈现设计并获得用户批准之前，不可调用任何实现 skill、编写任何代码、搭建任何项目、运行 init_project.py 或采取任何实现行动。这适用于每个项目，无论其看起来多简单。
</HARD-GATE>

## 反模式："SRS 够详细可以直接编码了"

SRS 描述系统必须做什么（WHAT）。设计文档描述如何做（HOW）。即使需求清晰，实现方案（架构、数据模型、技术栈选择）也需要明确的决策和用户批准。跳过设计会导致会话中期修正和返工。

## 检查清单

你必须为以下每项创建 TodoWrite 任务并按顺序完成：

1. **阅读已批准的 SRS** — 从 `docs/plans/*-srs.md`
2. **探索技术上下文** — 现有代码、框架、运行环境
3. **提出 2-3 种方案** — 含权衡和你的推荐
4. **逐章节设计批准** — 架构、数据模型、API、UI、测试
5. **编写设计文档** — 保存到 `docs/plans/YYYY-MM-DD-<topic>-design.md` 并提交
6. **过渡到 Init** — **必需子 SKILL：** 调用 `long-task:long-task-init`

**终态是调用 long-task-init。** 不可调用任何其他实现 skill。

## Step 1：阅读 SRS 并提取设计输入

1. 从 `docs/plans/*-srs.md` 读取已批准的 SRS 文档
2. 提取关键设计驱动因素：
   - **功能范围** — FR 数量、优先级分布、依赖链
   - **约束** — 限制技术/方案选择的硬性限制
   - **接口需求** — 需集成的外部系统、协议、数据格式
   - **用户画像** — 影响 API 设计决策的技术水平
3. 列出任何必须在设计前解决的 SRS **开放问题**
   - 若未解决的问题影响架构 → 在 Step 2 前通过 `AskUserQuestion` 询问用户

## Step 2：探索技术上下文

1. 探索项目将构建的现有代码/仓库
2. 识别 SRS 中未涉及的技术约束（如 monorepo 结构、现有库）
3. 检查设计文档模板：
   - 若用户指定了模板路径 → 读取并验证
   - 否则 → 读取 `docs/templates/design-template.md`（此 skill 附带的默认模板）
   - **验证**：模板必须是包含至少一个 `## ` 标题的 `.md` 文件

## Step 3：提出方案

呈现 **2-3 种实现方案**及明确权衡：

```markdown
## Approach A: [Name]
**How it works**: [1-2 sentences]
**Pros**: [bullet list]
**Cons**: [bullet list]
**Best when**: [conditions]
**Third-party dependencies**: [key libraries/frameworks this approach requires, with versions]

## Approach B: [Name]
...

## Recommendation: Approach [X]
**Reason**: [why this fits best given the SRS constraints]
```

**要点**：每个方案必须对照 SRS 约束评估。

## Step 4：逐章节批准

对非平凡项目，将设计拆分为章节并逐章节批准：

0. **项目结构** — 目标项目目录树，标记 [existing] / [new] / [modified] 条目
   - 新建项目：展示计划的目录布局
   - 存量项目：先探索现有代码库（Step 2），然后标记此设计将添加或修改的目录/文件
1. **架构** — 系统组件、逻辑视图、技术栈决策
   - 必须包含**逻辑视图**（Mermaid `graph`）展示层/包/模块及依赖方向
   - 必须包含**组件图**（Mermaid `graph`）展示运行时组件及交互
   - 必须对照 SRS 约束论证技术栈选择
2. **关键功能设计** — 每个关键功能或功能组一章
   - 每个功能章至少必须包含：
     - **类图**（Mermaid `classDiagram`）— 类/模块、属性、方法、关系
     - **一个行为图**：序列图（Mermaid `sequenceDiagram`）或流程图（Mermaid `flowchart`）
     - **集成面**（§4.N.6）— 声明 Provides/Requires 表并引用 §6.2 Contract ID；若无跨功能依赖则写"Self-contained"
   - 对复杂功能，包含全部四个视图：类图、序列图、流程图和设计说明
   - 所有图表必须使用 **Mermaid** 格式 — 不要 ASCII 艺术或图片引用
3. **数据模型** — schema、关系、存储策略
   - 适用时必须使用 Mermaid ER 图（`erDiagram`）
4. **API / 接口设计**
   - **外部接口**（§6.1）— 端点、契约、协议（追溯到 SRS IFR-xxx）
   - **内部 API 契约**（§6.2）— 功能间边界；§3.3 组件图的每条边必须有对应的 §6.2 行，含 Contract ID、请求/响应 schema 和错误码
5. **第三方依赖** — 所有库/框架的**确切版本号**
   - 必须验证依赖间的兼容性
   - 必须验证与项目目标运行时版本的兼容性
   - 必须注明每个依赖的许可证类型
   - 对非平凡依赖链必须包含依赖图（Mermaid）
6. **测试策略** — 仅高层测试方案决策
   - 测试哲学：TDD（Red → Green → Refactor）
   - 工具选择：测试框架、覆盖率工具、变异工具（含版本 — 这些是设计决策）
   - 覆盖率阈值：行 >= X%，分支 >= Y%，变异 >= Z%
   - **边界**："详细测试场景在功能设计和 TDD 阶段定义 — 不在这里。"
7. **开发计划** — 里程碑、任务分解、优先级排序
   - 必须定义有明确退出标准的里程碑
   - 必须分解为上下文预算大小的功能（P0-P3）— §9.2 每行成为 `feature-list.json` 中的一个功能；将相关的已调整大小的 FR（已通过 SRS G+S 启发式验证）分组为垂直切片；包含 `Mapped FRs` 列以实现可追溯性
   - 必须展示依赖链（Mermaid `graph`）识别关键路径
   - 必须包含风险评估及缓解策略

> **功能定量在上游完成**：FR 在需求阶段通过双向粒度分析（G1-G6 拆分 + S1-S4 合并）调整大小。§9.2 将这些已调整大小的 FR 分组为实现功能。每行应将 1+ 个相关 FR 映射为一个垂直切片，高效利用一个 Worker 会话（~50% 上下文窗口，目标每 FR ~1,000 行实现代码不含 UT）。下方规模表中的功能数指最终 §9.2 行数。

呈现每个章节。等待用户反馈。整合变更后再进入下一个。

**对简单项目**（< 5 功能）：合并所有章节为单次批准步骤，但仍须包含必需的图表和依赖版本。

## Step 4b：填充 §11 — 代码库约定与约束

**始终执行此步骤** — 存量项目和新建项目均适用。§11 必须出现在每份设计文档中，以便下游 skill（feature-design、TDD、Worker）可以无条件读取。

**存量项目**（若 `docs/rules/` 存在且已填充 Phase 0-pre 扫描结果）：

1. **读取所有 `docs/rules/*.md` 文件** — `coding-style.md`、`coding-constraints.md`、`build-and-compilation.md`
2. **使用设计模板的 §11 结构填充设计文档的 §11**（代码库约定与约束）：
   - §11.1：从 `coding-constraints.md` 提取"强制内部库"表
   - §11.2：从 `coding-constraints.md` 提取"禁止的 API / 库"表
   - §11.3：从 `coding-constraints.md` 提取"批准的第三方库"表
   - §11.4：从 `coding-constraints.md` 提取"静态分析工具"表（仅工具名 + 配置路径 + 运行命令 — 不读取配置内容）
   - §11.5：从 `coding-style.md` 提取关键命名和格式规则（摘要表）
   - §11.6：从 `coding-constraints.md` 提取错误处理模式
   - §11.7：从 `build-and-compilation.md` 提取"测试与质量工具"表（测试框架、覆盖率工具、变异工具 — 仅工具名 + 配置路径 + 运行命令）
3. **交叉验证** — 检查扫描的约定与设计决策之间的冲突：
   - §8（第三方依赖）：新依赖不可与 §11.2 禁止列表冲突
   - §6.2（内部 API 契约）：使用的库必须符合 §11.1 内部库强制要求
   - 若存在冲突：标记"⚠ 设计覆盖：[原因]"并呈现给用户确认
4. **向用户呈现 §11** 以供审查（与其他章节相同的批准流程）

**新建项目**（若 `docs/rules/` 不存在或为空）：

1. **用空表填充 §11**（列标题 + 零行）适用于 §11.1-§11.7 每个子章节，使用设计模板的 §11 结构
2. **向用户呈现**："§11 已创建空约定表。如已知约束请现在添加，或留空 — 下游 skill 无条件读取 §11。"
3. 若用户添加约束：整合并重新呈现以获批准
4. 若用户留空：继续 — 空表向下游 skill 表示"无约束"

## Step 5：编写设计文档

保存已批准的设计到 `docs/plans/YYYY-MM-DD-<topic>-design.md`。

### 模板使用

读取 Step 2 中找到的模板（用户指定或默认 `docs/templates/design-template.md`）：
1. 保留模板的标题结构
2. 用批准的设计内容替换每个标题下的指导文本
3. 若尚无元数据则在顶部添加（`Date`、`Status`、`SRS Reference`、`Template` 路径）
4. 对模板中未覆盖的章节：标记"[不适用]"
5. 对无匹配模板章节的已批准内容：追加为"附加说明"

## Step 5b：设计集成一致性检查

过渡到 Init 之前，机械式验证跨功能集成一致性：

1. **契约完整性**：对 §3.3 组件图的每条边，验证 §6.2 内部 API 契约中存在对应行。标记缺失行。
2. **Schema 一致性**：对每个 §6.2 行，验证 Provider 功能的 §4.N 类图包含 Response Schema 类型，且 Consumer 功能的 §4.N 引用 Request Schema。标记不匹配。
3. **依赖完整性**：对每个出现在 §6.2 "Consumer" 列中的功能，验证它在 §9.3 依赖链中列出了 Provider 功能 ID。标记缺失的依赖边。

向用户呈现任何标记的问题。在进入 Init 前解决。

## Step 6：过渡到 Init

设计文档保存并提交后：

1. 总结 Init skill 需要的关键输入：
   - **来自 SRS**：需求、验收标准 → 功能
   - **来自设计**：技术栈、架构 → 项目骨架
2. **必需子 SKILL：** 调用 `long-task:long-task-init` 以搭建项目

## 设计阶段规模

| 项目规模 | 功能数 | 设计深度 |
|---------|--------|---------|
| 微型 | 1-5 | 单段方案 + 1 次批准步骤；逻辑视图 + 1 个功能图 + 依赖表 + 简化开发计划 |
| 小型 | 5-20 | 2-3 个方案选项 + 合并章节批准；逻辑视图 + 关键功能图 + 依赖表 + 里程碑计划 |
| 中型 | 20-50 | 完整多章节批准；所有架构视图 + 逐功能图 + 完整依赖分析 + 详细开发计划 |
| 大型 | 50-200+ | 完整多章节批准；每个功能组全面图表 + 依赖兼容矩阵 + 分阶段开发计划含风险登记簿 |

## §4 深度策略

对功能多的项目，§4.N 章节按不同深度编写以管理上下文窗口约束：

| 项目规模 | 每功能 §4.N 内容 |
|---------|-----------------|
| 小型（< 20） | 完整：概述 + 类图 + 行为图 + 设计说明 + 集成面 |
| 中型（20-50） | P0/P1 功能完整；P2/P3 功能精简 |
| 大型（50+） | 所有功能精简：概述 + 关键类型 + 集成面 |

**精简 §4.N 格式：**

```markdown
### 4.N Feature: <Name> (FR-xxx)
#### 4.N.1 Overview
[1-2 sentences]
#### 4.N.2 Key Types
[List the main classes/types this feature introduces, with one-line purpose each]
#### 4.N.6 Integration Surface
[Provides/Requires tables referencing §6.2]
```

这是安全的，因为 feature-design SubAgent（Worker Step 4）能访问 §6.2 契约并产出完整的类/序列/流程/算法设计。精简 §4.N 作为**集成规格**而非完整设计。

## 危险信号

| 合理化 | 正确回应 |
|--------|---------|
| "SRS 已经暗示了架构" | SRS 描述 WHAT 而非 HOW。呈现选项。 |
| "只有一种构建方式" | 至少呈现 2 种方案。即使显而易见的选择也受益于明确的权衡。 |
| "我已经知道最佳方案" | 呈现选项，让用户选择 |
| "用户似乎不耐烦，我跳过设计" | 简要解释价值，然后高效执行 |
| "我边做边设计" | 前期设计比会话中期修正更便宜 |
| "让我在这里重新澄清需求" | 需求属于 SRS。若缺失，标记为开放问题并在设计前与用户解决。 |

## 图表要求

所有架构和设计视图必须使用 **Mermaid** 语法。这确保：
- 图表与文档一起版本控制（无外部图片文件）
- 图表可在 GitHub、GitLab 和大多数 Markdown 查看器中渲染
- 图表与设计变更保持同步

### 必需图表类型

| 章节 | 图表类型 | Mermaid 语法 | 必需？ |
|------|---------|-------------|--------|
| 架构逻辑视图 | 分层包图 | `graph TB` | 始终 |
| 架构组件 | 组件交互 | `graph LR` | 始终 |
| 关键功能 — 结构 | 类图 | `classDiagram` | 每功能 |
| 关键功能 — 行为 | 序列图 | `sequenceDiagram` | 每功能（至少一个行为图） |
| 关键功能 — 逻辑 | 流程/决策图 | `flowchart TD` | 每功能（至少一个行为图） |
| 数据模型 | ER 图 | `erDiagram` | 若有持久存储 |
| 依赖图 | 依赖树 | `graph LR` | 若 > 3 个第三方依赖 |
| 开发计划 | 关键路径 | `graph LR` | 始终 |

### 图表质量检查清单
- [ ] 每个图表有清晰标题或周围标题
- [ ] 类图展示可见性修饰符（`+`/`-`/`#`）和关键方法
- [ ] 序列图展示主成功路径和至少一个错误路径
- [ ] 流程图包含所有分支逻辑的决策节点
- [ ] 无占位符图表 — 每个图表反映实际批准的设计内容
- [ ] §3.3 组件图的每条边包含引用 §6.2 的 Contract ID
- [ ] 增量更新期间：新增/修改的图表元素使用视觉变更跟踪样式（绿色=NEW，琥珀色=MODIFIED），按设计模板约定；移除前一批次标记

## 第三方依赖规则

1. **必须精确版本** — 指定 `1.2.3` 或约束范围 `^1.2.0` / `>=1.2,<2.0`；绝不使用 `latest` 或省略版本
2. **兼容性矩阵** — 验证每个依赖与以下兼容：
   - 目标语言/运行时版本（如 Python >= 3.10, Node >= 18）
   - 栈中其他依赖（检查已知冲突）
3. **许可证审计** — 记录每个依赖的许可证；标记可能与项目需求冲突的 copyleft 许可证（GPL, AGPL）
4. **升级路径** — 注明任何接近 EOL 或有已知迁移问题的依赖

## 开发计划规则

开发计划章节桥接设计文档到 Init 阶段。必须包含：

1. **里程碑** — 有明确范围和退出标准的时间框定阶段
   - M1 始终是"基础"（项目骨架、CI、核心抽象）
   - 最终里程碑始终是"润色与发布"（文档、示例）
2. **任务分解** — 功能映射到优先级（P0-P3）及理由
   - P0：基础 — 所有其他功能所需
   - P1：核心价值 — 最小可行功能集
   - P2：扩展 — 重要但不阻塞发布
   - P3：锦上添花 — 时间线紧则延迟
3. **依赖链** — Mermaid 图展示哪些功能阻塞其他功能
4. **配对功能排序** — 当项目同时有后端和前端功能时，组织任务分解表使每个后端功能与其对应前端功能配对。这产生自然的开发流程：Backend A → Frontend A → Backend B → Frontend B。Init 阶段使用此配对在 `feature-list.json` 中排序功能。
5. **风险登记簿** — 技术和进度风险及缓解措施

Init 阶段使用此计划以正确的优先级排序、配对分组和依赖链填充 `feature-list.json`。

## 集成

**调用者：** using-long-task（当 SRS 存在、无设计文档、无 feature-list.json 时）
**要求：** `docs/plans/*-srs.md` 中已批准的 SRS；可选 `docs/rules/*.md`（Phase 0-pre 扫描的代码库约定）
**链接到：** long-task-init（设计批准后）
**产出：** `docs/plans/YYYY-MM-DD-<topic>-design.md`（始终包含 §11 代码库约定 — 存量项目从 `docs/rules/` 填充，新建项目为空表）
